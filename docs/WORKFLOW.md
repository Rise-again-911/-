# 开发过程思路 & 工作流说明

> 100种不可思议旅行 — 72 小时 AI 辅助开发面试考核项目

---

## 1. 开发流程：Claude Code + Superpowers 多范式工作流

本项目的 AI 辅助开发并未使用 Deepseek V4 Pro，而是全程使用 **Claude Code（Claude Sonnet 4.6 1M context）** 作为唯一的 AI 编程助手。整个开发过程遵循一套严格的工程化工作流，核心工具链为：

- **Claude Code CLI**：作为主控端，接收用户指令并调度子 agent 执行具体任务。
- **Superpowers 技能体系**：一组内置的工程化 skill（brainstorming、subagent-driven-development、ui-ux-pro-max、test-driven-development 等），用于在不同阶段约束 AI 行为。
- **Claude Preview**：本地开发服务器的浏览器预览环境，用于实时验收 UI 组件和页面。

### 工作流总览

```
用户指令（阶段化 Prompt）
        │
        ▼
┌──────────────────────────────────┐
│  Claude Code（主控 Agent）        │
│  - 解读指令                       │
│  - 读取计划文件                    │
│  - 创建 Task 列表                 │
│  - 逐步调度子 Agent               │
└──────────┬───────────────────────┘
           │
    ┌──────┴──────┬──────────────┬─────────────┐
    ▼             ▼              ▼             ▼
  SDD Agent   DDD Agent     TDD Agent     E2E Agent
  (文档生成)   (UI/UX+组件)  (测试编写)    (端到端)
```

每一阶段的 Agent 只拿到与本阶段相关的上下文（计划片段 + 约束规则），不继承之前阶段的会话历史。这迫使每个 Agent 在"干净"的上下文中工作，避免了上下文污染和范围蔓延。

### 关键设计原则

**1. 阶段隔离，逐段递进。** 项目被拆为 11 个阶段，每个阶段启动前明确边界、产出和禁止项。阶段完成后停止，不允许自动进入下一阶段——这是人工 checkpoint，防止 AI 一次性生成大量不可验证的代码。

**2. 四份真理文档不可变。** PRD、ERD、API_CONTRACT、SAD 被定义为"不变量"。任何实施阶段都不能修改这四份文档，确保设计基线在整个开发过程中保持一致。

**3. UI/UX 由技能库约束。** 涉及组件和页面的阶段强制调用 `ui-ux-pro-max` skill。该技能内置 67 种风格、96 种调色板、57 种字体搭配和 99 条 UX 规范，为 AI 提供结构化的设计决策依据，而非依赖其"审美直觉"。

**4. 验收驱动开发。** 每个 Task 都附带明确的验收命令（`npx tsc --noEmit`、`Invoke-RestMethod`、`preview_snapshot`、`preview_eval` 等），AI 在完成后必须执行验证并汇报结果，而非凭"感觉"声称完成。

## 2. 与 AI 协同中遇到的典型问题及解决路径

### 问题一：未完成任务就自己停下来

**现象**：在执行多步骤阶段（如阶段 8、阶段 9）时，Claude 经常在完成任务列表中的前 2-3 个 Task 后就停下来，主动向用户汇报"阶段 X 部分完成"并询问是否继续，而不是按 subagent-driven-development 规则将全部 Task 一口气执行完毕。

**根因分析**：Claude 的默认行为倾向于"阶段化交互"——它会在每个有意义的节点停下来等待反馈。subagent-driven-development skill 虽然要求"连续执行、不中断"，但当阶段 Task 数量多（阶段 9 有 12 个 Task）或上下文消耗较大时，Claude 会倾向于提前结束当前回合，而非继续驱动下一个 Task。

**解决路径**：
1. 在每个阶段的 Prompt 结尾明确写"继续执行"或"全都继续执行"来推动 AI 前进。
2. 将"完成后停止"限定为阶段级别的停止（即整个阶段所有 Task 完成后再停止汇报），而非单个 Task 完成就停止。
3. 如果 AI 在中间停下，不需要重新描述整个阶段，只需回复"继续执行"即可让它从断点继续。

**教训**：subagent-driven-development 的"连续执行"依赖 AI 的回合持续性。当回合输出接近上限或 Task 数量较大时，需要在 Prompt 末尾显式推动。把"继续执行"作为阶段 Prompt 的固定结尾句是一个有效的防停措施。

---

### 问题二：反复运行 echo ok / echo done 等无意义命令

**现象**：Claude 在执行完一阶段代码后，有时会自发执行 `echo "ok"`、`echo "done"`、`echo "PASS"` 或 `echo "TEST_SUCCESS"` 等无意义 shell 命令。这些命令不产生任何验收价值，但会触发权限提示、增加不必要的工具调用，浪费时间和 token。

**根因分析**：这是 Claude 在"验证"行为上的一种低质量习惯——它想表达"完成了"，但选择了无意义的 echo 作为表达方式，而非执行真正有验证能力的命令（如 `npx tsc --noEmit` 或 `preview_eval`）。本质上是将"声明完成"和"验证完成"混淆了。

**解决路径**：
1. 在每个阶段的限制中显式加入：`不要运行 echo "ok" 或 echo "done" 这种无意义命令`——这一条在本项目的所有阶段 Prompt 中都已成为固定条款。
2. 当 Claude 仍然执行了这类命令时，忽略该行输出，不将其计入有效验证。
3. 要求每个任务完成后执行有实际验证能力的命令（类型检查、API 守卫测试、DOM 结构验证），不给 echo 留空间。

**教训**：AI 的"完成仪式"需求不能靠 echo 满足，而应该引导到真正的验证命令。在 Prompt 中提前禁止无意义命令，比事后纠正更有效。

---

### 问题三：执行完任务后没有任何反馈和回复

**现象**：经常出现 Claude 执行完一阶段的所有 Task 后，最后一个工具调用（如 `npx tsc --noEmit`）返回空结果，然后 Claude 就静默了——不再输出任何文字回复，不汇报完成状态，不列出创建/修改的文件，也不说"是否继续"。用户无法判断是任务在执行中、已完成未汇报、还是中途卡住了。

**根因分析**：Claude 在处理大量连续工具调用时，有时会长考一段内容后在思考结束点就停止输出，而不是生成一个总结性的文字回复。这在 Task 数量多（如阶段 9 有 12 个 Task）、工具调用密集的阶段尤其明显。另外，如果最后一个工具调用恰好没有输出（如 `tsc --noEmit` 成功返回空），Claude 可能判断"已完成"而跳过了文字总结。

**解决路径**：
1. 在每个阶段的最终汇报要求中明确规定："创建/修改了哪些文件、Task 是否全部完成、执行了哪些有效验证命令、是否存在遗留问题、是否可以提交"——这些是必须用文字回答的问题，迫使 Claude 生成文字回复。
2. 用户看到静默时，只需回复"继续"或"继续执行"，Claude 会从中断点续上并输出汇报。
3. 在 Prompt 中增加一句"完成后请输出文字汇报，不要只执行静默命令"。

**教训**：工具调用序列的最后一步不应该是一个可能返回空结果的命令（如 `tsc --noEmit`），而应该是一个迫使 AI 生成文字输出的要求。最终的"文字汇报模板"本身就是为了解决这个问题而设计的——它把汇报从"AI 觉得应该说什么"变成了"必须回答的问卷"。

---

### 问题四：AI 的"顺手改"倾向——范围蔓延

**现象**：在执行阶段 6（UGC 投稿与评论）时，AI 在实现 CommentSection 后发现 `useSession` hook 需要 `<SessionProvider>` 包装器，而 `src/app/layout.tsx` 中没有。AI 直接创建了 `AuthProvider.tsx` 并修改了 `layout.tsx`——这两个文件不在阶段 6 的原始产出列表中。

**根因分析**：AI 的行为逻辑是"依赖满足"——它发现了功能依赖（`useSession` → `SessionProvider` → `layout.tsx`），就自动补齐。这在技术上是正确的，但在工作流管理上是"越界"。

**解决路径**：
1. 在阶段 Prompt 中明确"允许修改的文件范围"，超出范围必须先说明原因。
2. 接受必要的越界修改（AuthProvider 确实是 CommentSection 的硬依赖），但在事后补充文档记录——在实施计划和 SAD 中追认这个改动。
3. 在后续阶段的限制中增加具体化的"不要实现 X"条款，不给 AI 留下判断空间。

**教训**：对于工程化 AI 开发，"禁止做什么"比"做什么"更难写，但同样重要。一个好的阶段 Prompt 应该把禁止项写得像代码中的 assertion 一样明确。

### 问题五：UI 验收的"视觉幻觉"——中文 IME 与筛选失败

**现象**：阶段 10 首页完整集成完成后，AI 汇报"搜索通过、筛选通过、盲盒通过"。但实际验收发现：(1) 中文输入时拼音直接写入搜索词框，未完成选字就触发搜索；(2) 标签筛选调用不存在的 `/api/trips/filter` 接口，导致"加载失败"；(3) 盲盒按钮只有一个 `#` 符号，用户完全不知道它是干什么的。

**根因分析**：AI 的"完成感"来自于它写了调用 API 的 fetch 代码并做了类型检查。但它没有真正在浏览器中使用中文输入法测试，也没有以普通用户视角审视盲盒按钮的可理解性。

**解决路径**：
1. 切换验收方式——从 `preview_screenshot`（不稳定）切换到 `preview_snapshot` + `preview_eval`（结构化、可读取 DOM 文本）的组合。
2. 针对每个具体问题写修复 Prompt：IME 需要 `onCompositionStart/End` 处理；筛选需要改为前端本地筛选而非调用不存在接口；盲盒需要从纯图标改为"随机发现"文字按钮。
3. 修复后重新运行 E2E 测试作为回归验证。

**教训**：AI 的代码静态分析能力很强（类型检查、import 路径），但缺乏"用户视角"的体验感知。工程化 AI 开发必须将视觉和交互验收拆成具体的、可自动化的检查点，而不能依赖 AI 的"我觉得好看"。

### 问题六：E2E 测试的"选择器脆弱性"

**现象**：Playwright 首次运行 13 个 E2E 测试中有 5 个失败。根因是 `LoginForm` 组件的 input 缺失 `name` 属性，导致 `input[name="username"]` 选择器匹配不到元素。另一个问题是 `text=反向小城` 匹配到 4 个元素触发 strict mode。

**根因分析**：AI 在 DDD 阶段实现 LoginForm 时使用了 `id` 作为标识符（`id="login-username"`），但没有添加 `name` 属性。这对功能完全无影响，但 E2E 测试编写时遵循的是 Playwright 最佳实践——优先使用 `name` 属性作为稳定选择器。

**解决路径**：
1. 遵循 Prompt 原则——"如果测试暴露了真实问题，最小化修改业务代码"。给两个 input 添加 `name="username"` 和 `name="password"`，不改变任何功能或 UI。
2. 对 E2E 测试本身，将多匹配的 `text=反向小城` 改为唯一文本 `text=个结果`。
3. 两个修改都在 3 行以内，且完全可解释。

**教训**：这暴露了 DDD 和 E2E 阶段之间的"契约断层"——DDD 阶段没有考虑可测试性（如 name 属性），E2E 阶段发现了这个缺口。工程化 AI 开发应该将"可测试性"作为组件验收标准的一部分，而非事后补丁。

## 3. 对"工程化 AI 开发"的理解
：

### 3.1 AI 不是程序员，是工具链

把 AI 当成一个程序员来管理（"帮我写个功能"）是低效的。更有效的做法是把 AI 当成一个**可编程的工具链**——它需要被 Pre-prompt（技能/规则）约束、被计划文件引导、被验收命令验证、被阶段边界隔离。本项目中，Superpowers 技能体系承担了"编译器"的角色：把人类意图编译成 AI 可执行的约束指令。

### 3.2 阶段化 + Checkpoint 是核心模式

AI 的最大风险不是写出错误代码，而是在错误方向上持续生成大量代码。阶段化 + checkpoint 模式（每阶段停止汇报、人工确认后才进入下一阶段）是应对这个风险的最有效手段。它把一个大型任务拆成多个可验证的小型交付，降低了"越走越偏"的概率。

### 3.3 验收标准必须可自动化

"看起来不错"不是验收标准。每条验收标准必须能转化为一行命令或一个可预测的输出。本项目中使用的验收手段包括：
- `npx tsc --noEmit`（类型检查）
- `node -e "fetch(...)"` （API 端点守卫）
- `npx vitest run`（单元测试断言）
- `npx playwright test`（E2E 流程验证）
- `preview_snapshot` / `preview_eval`（DOM 结构验证）

这些手段的共同特征是：AI 可以直接执行并拿到明确的通过/失败结果，不需要人类主观判断。

### 3.4 文档先行，代码后行

四份真理文档（PRD/ERD/API_CONTRACT/SAD）是整个项目的"宪法"。任何代码变更都可以回溯到某一文档的某一条款。这种契约式开发方式让 AI 在实现时有明确的参照系，也让代码审查时有统一的评判标准。在 72 小时的紧张时间线中，花 6-8 小时写文档看似"慢"，但实际节省了后续阶段的大量调试和返工时间。

### 3.5 AI 擅长执行，不擅长决策

本项目中所有"该怎么办"的决策都由人工做出（选择什么技术栈、MVP 包含哪些功能、UI 走什么风格），然后写成 Prompt 交给 AI 执行。AI 的角色是"高能力执行者"而非"架构决策者"。这种分工让人类保持对项目方向的完全掌控，同时利用 AI 的执行效率覆盖大量机械性的编码、测试和文档工作。

## 4. 工作流示意

```
┌──────────────────────────────────────────────────────────┐
│                     人类决策层                            │
│  产品方向 · 技术选型 · 功能边界 · 视觉风格 · 阶段规划     │
└──────────────────────┬───────────────────────────────────┘
                       │ Prompt / 计划文件
                       ▼
┌──────────────────────────────────────────────────────────┐
│                   Claude Code 主控层                      │
│  解读计划 · 调度子 Agent · 执行验收 · 汇报结果             │
└──────────────────────┬───────────────────────────────────┘
                       │
       ┌───────────────┼───────────────┬───────────────┐
       ▼               ▼               ▼               ▼
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  SDD     │    │  DDD     │    │  TDD     │    │  E2E     │
│  文档    │    │  组件    │    │  测试    │    │  测试    │
│  模型    │    │  页面    │    │  校验    │    │  流程    │
└────┬─────┘    └────┬─────┘    └────┬─────┘    └────┬─────┘
     │               │               │               │
     └───────────────┴───────────────┴───────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────┐
│                     验收闭环                              │
│  tsc · vitest · playwright · preview · git status        │
└──────────────────────────────────────────────────────────┘
```

**核心思想**：人类做决策，AI 做执行，文档做契约，测试做验证，阶段做边界——这是一个完整的工程化 AI 开发体系。
